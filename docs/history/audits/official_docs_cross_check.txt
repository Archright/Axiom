## 3. POSIX setrlimit (`scripts/gate_hook.nim`, `scripts/gate_replay.nim`)
================================================================================

### Official Docs (https://pubs.opengroup.org/onlinepubs/9699919799/functions/setrlimit.html)
- **RLIMIT_NOFILE**: "number one greater than the maximum value that the system
  may assign to a newly-created file descriptor"
- **rlim_cur vs rlim_max**: 
  - `rlim_cur` (soft limit): may be changed to any value ≤ hard limit
  - `rlim_max` (hard limit): may be irreversibly lowered; only privileged processes can raise
- **Return value**: 0 on success, -1 on error with `errno` set
- **Errors**: `EINVAL` (invalid resource, or `rlim_cur > rlim_max`), `EPERM` (privilege)
- **APPLICATION USAGE**: "If a process attempts to set RLIMIT_NOFILE to less than
  the highest currently open fd + 1, unexpected behavior may occur"

### Implementation: `scripts/gate_hook.nim`
```nim
proc raiseRlimitNoFile() {.raises: [].} =
  var rlim: Rlimit
  rlim.rlim_cur = 65536
  rlim.rlim_max = 65536
  discard setrlimit(RLIMIT_NOFILE, rlim)
```
- ✅ Sets both `rlim_cur` and `rlim_max` to 65536 — correct pattern
- ✅ Called in `main()` before any malebolgia spawn (line 280)
- ✅ Uses `RLIMIT_NOFILE` constant — correct resource
- ✅ `{.raises: [].}` — guarantees no exceptions

### DISCREPANCY 5 [MEDIUM]: Return value of setrlimit is discarded
- **Finding**: Both `scripts/gate_hook.nim` (line 25) and `scripts/gate_replay.nim`
  (line 189) use `discard setrlimit(...)`. Per POSIX docs, `setrlimit` returns -1
  on error and sets `errno`. If the process does not have `CAP_SYS_RESOURCE`
  (which is almost always the case), lowering the hard limit from the system
  default (often much higher than 65536) is fine, but raising it would require
  privileges. The current code silently ignores failure.
- **Severity**: MEDIUM — if `setrlimit` fails (e.g., running in a container with
  restricted rlimits), the FD limit remains at 1024, and malebolgia will fail
  with `EMFILE` errors. The error will manifest as a cryptic malebolgia exception
  rather than a clear "setrlimit failed" message.
- **Recommendation**: At minimum, log a warning on failure:
  ```nim
  if setrlimit(RLIMIT_NOFILE, rlim) != 0:
    stderr.writeLine("[WARN] setrlimit(RLIMIT_NOFILE, 65536) failed: " & $osLastError())
  ```

### DISCREPANCY 6 [INFO]: Hard limit == soft limit (65536)
- Per POSIX, setting `rlim_max = rlim_cur = 65536` is fine — this is a common pattern.
  The hard limit is set to the same value as the soft limit, which means the limit
  cannot be raised again without privileges. This is acceptable.

### Implementation: `scripts/gate_replay.nim`
- ✅ Same pattern as gate_hook (lines 186-189)
- ✅ Matches the documented fix in `docs/history/malebolgia_fd_root_cause_analysis.md`
- ❌ Same `discard` issue (DISCREPANCY 5 applies here too)
- ❌ `setrlimit` is called after `compileNimtryGate` but before malebolgia — correct ordering

## 4. Git Worktree (`scripts/gate_replay.nim`)
================================================================================

### Official Docs (https://git-scm.com/docs/git-worktree)
- **Add**: `git worktree add [-f] [--detach] [--checkout] <path> [<commit-ish>]`
- **Remove**: `git worktree remove [-f] <worktree>`
  - "Only clean worktrees (no untracked files and no modification in tracked files)
    can be removed. Unclean worktrees or ones with submodules can be removed with --force."
- **Lock**: Prevents pruning; useful for portable devices
- **Prune**: Auto-removes stale admin files; configurable via `gc.worktreePruneExpire`
- **DETAILS**: Each linked worktree has a private sub-directory under
  `$GIT_DIR/worktrees/<basename>`
- **Warning**: If a working tree is deleted manually, admin files remain until pruned

### Implementation: `scripts/gate_replay.nim`
```nim
proc replayCommit(...) =
  let worktree = &"/tmp/gate-replay-{pid}-{shortHash}"
  
  # Clean up any leftover from previous runs
  if dirExists(worktree):
    discard execCmdEx(&"git worktree remove --force {worktree} 2>&1")
  
  # Add worktree for this commit
  let (_, addCode) = execCmdEx(
    &"git worktree add --force {worktree} {commit} 2>&1")
  
  # ... do work ...
  
  # Cleanup worktree
  discard execCmdEx(&"git worktree remove --force {worktree} 2>&1")
```

### DISCREPANCY 7 [MEDIUM]: Pre-emptive cleanup may remove a legitimate worktree
- **Finding**: Line 110-111 attempts `git worktree remove --force` on a leftover
  directory that matches the pattern. If a legitimate worktree happens to exist
  at `/tmp/gate-replay-{pid}-{shortHash}` (e.g., from a different tool), it
  would be forcibly removed.
- **Severity**: MEDIUM — in practice, the path includes the PID and short hash,
  so collision risk is low. However, `--force` removes even dirty worktrees,
  which could cause data loss.
- **Recommendation**: Use `git worktree remove {worktree}` without `--force`
  for the pre-emptive cleanup, and only use `--force` for the post-use cleanup
  (where we know the worktree is ours).

### DISCREPANCY 8 [MINOR]: No lock on worktrees during processing
- **Finding**: The worktree is created, used, and removed without locking.
  Per git-worktree docs, `gc.worktreePruneExpire` controls how long stale admin
  files survive. If `git gc` runs between worktree creation and removal, it
  could prune the worktree's admin files.
- **Severity**: MINOR — race condition window is extremely small and unlikely
  in practice since the operation is fast.

### DISCREPANCY 9 [MINOR]: Exit code for worktree commands discarded
- **Finding**: The worktree `remove` and pre-emptive cleanup use `discard execCmdEx(...)`,
  ignoring exit codes. If `git worktree remove` fails, stale worktrees accumulate.
- **Severity**: MINOR — stale worktrees would be cleaned by subsequent runs'
  pre-emptive cleanup. However, repeated failures could cause accumulation.
- **Recommendation**: At minimum, log failures to stderr.

### DISCREPANCY 10 [INFO]: `--force` flag usage
- `git worktree add --force` (line 115): bypasses the "already checked out" check.
  This is intentional — gate_replay checks out commits that may be on existing branches.
- `git worktree remove --force` (line 112, 151): bypasses the "clean worktree" check.
  This is correct for throwaway worktrees where we don't care about state.

### DISCREPANCY 11 [MINOR]: "Incremental" in `gate_replay.nim` is a misnomer
- **Finding**: `scripts/gate_replay.nim` line 130 comment says "Incremental nim check"
  but this is not truly incremental in the Nim compiler sense. It runs `nim check`
  individually on each changed file, which processes the full import graph per file.
- **Severity**: MINOR — the term "incremental" here means "only checking changed files"

  The current approach (per-file or full-tree) is a correct alternative.
- **Severity**: INFO — the `--incremental` flag is experimental and may not work
  reliably with `nim check` (it targets the compiler's code generation step).
  Current approach is correct.
