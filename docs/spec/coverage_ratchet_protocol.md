**Related**: AGENTS.md §0.9 (Theater Prohibition), `docs/spec/environment_inputs.md` (§2.6 Ratchet env — signed-request binding), `src/gate/manifest.d/coverage-ratchet-gate.json`, `data/reliability_score.json`

## Purpose

The Coverage Ratchet Gate enforces a monotonicity invariant on test coverage:
**coverage can only increase**. Any regression is a gate failure unless a
formal, audited downgrade is executed.

## Authority Model

The ratchet floor (`baseline_coverage_pct` in `data/reliability_score.json`)
is an authority surface. Two operations move it, and only two:

| Operation | Authority | Binding |
|---|---|---|
| **Bump upward** (auto) | The gate itself, on `current >= baseline` | Deterministic: the floor can only rise to freshly measured coverage |
| **Downgrade** (exceptional) | A human administrator, via an **Ed25519 signature over a pinned key** | Signature payload binds the downgrade to this exact tree and baselines (§Admin Signature) |

Ambient environment (`AXIOM_RATCHET_DOWNGRADE`, `AXIOM_RATCHET_REASON`) is
**downgraded to a request channel only**. Setting the variables signals
*intent* to downgrade; it grants no authority. Without a valid admin
signature, no downgrade and no baseline lowering can occur on any path
(request-only semantics; see §Downgrade Protocol). This is the ratchet-specific
application of the DEBT#478 closure principle — *no unaudited ambient input may
influence a gate verdict on any path* ([docs/spec/environment_inputs.md](environment_inputs.md), Principle).

Note: `gracePeriodUntil` (`src/gate/gate_contract.nim`) is a **separate
mechanism** — it only softens a gate's severity (`gsError` → warning) during a
declared window. It is not part of the ratchet approval chain; downgrade
authorization is carried exclusively by the signed payload's `expires_at`.

## Ratchet Semantics

The gate reads `data/reliability_score.json` for the current baseline
coverage percentage and compares it against freshly-measured coverage
from `data/coverage_report.json` (generated by `bin/measure_coverage`).

### Comparison Rules

| Condition | Outcome |
|---|---|
| `current >= baseline` | **PASS** — baseline is bumped upward to `current` |
| `current < baseline` | **FAIL** — ratchet violation, unless downgrade protocol is satisfied |

### Auto-Update (Baseline Bump)

When current coverage exceeds the baseline, the gate automatically updates
`baseline_coverage_pct` in `data/reliability_score.json` to the new value.
This ensures the floor only rises over time. Upward bumps require no
signature: they are the ratchet's normal, monotone direction.

## Downgrade Protocol

A coverage downgrade is an **exceptional, audited operation**. The ambient
variables constitute a *request*, never an authorization:

| Variable | Required Value | Purpose |
|---|---|---|
| `AXIOM_RATCHET_DOWNGRADE` | `1` | **Requests** a downgrade (intent signal only) |
| `AXIOM_RATCHET_REASON` | Non-empty string | Justification carried into the audit record |

Setting both variables with current coverage < baseline does **not** by itself
lower the baseline. The downgrade executes only when the *signed approval*
defined in §Admin Signature is present and verifies against the pinned key;
otherwise the gate **fails closed** (ratchet violation, exit code 1).
Authorization semantics: `AXIOM_RATCHET_DOWNGRADE`/`AXIOM_RATCHET_REASON` are
request-scoped ([docs/spec/environment_inputs.md](environment_inputs.md) §2.6);
no environment value may substitute for the signature.

### Audit Trail

Every downgrade — and every **rejected** downgrade attempt — produces a JSONL
entry in `.axiom/bypass_audit.jsonl`. Audit failure (the record cannot be
written) means the downgrade is **refused**: the audit write is a
precondition, not a side effect (fail-closed audit; [NIST AU-9](https://csrc.nist.gov/pubs/sp/800/53/r5/upd1/final),
[OWASP Authentication Cheat Sheet — deny by default](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html)).

Minimum record requirements ([NIST AU-8](https://csrc.nist.gov/pubs/sp/800/53/r5/upd1/final)
contents; [NIST AU-10](https://csrc.nist.gov/pubs/sp/800/53/r5/upd1/final)
protection):

```json
{
  "tool": "coverage-ratchet-gate",
  "action": "baseline_downgrade",
  "outcome": "accepted | rejected",
  "old_baseline": 15.4,
  "new_baseline": 14.2,
  "reason": "Removed dead test file after architecture cleanup",
  "admin_signature": "<full Ed25519 signature, base64>",
  "signing_key_id": "<id of the pinned verification key>",
  "timestamp": "2026-10-07T12:00:00Z",
  "prev_record_hash": "<SHA-256 of the previous audit record — hash chain>",
  "commit_hash": "abc123def456..."
}
```

- `timestamp` is UTC ISO 8601.
- `admin_signature` carries the **full signature** plus the `signing_key_id`
  that identifies which pinned key produced it — the audit record alone must
  be sufficient to re-verify the approval offline.
- `prev_record_hash` chains every record to its predecessor, so removal or
  retro-editing of any historical record breaks the chain detectably.
- Both verification successes and verification **failures** are recorded
  (rejected attempts keep their reason, the offered signature, and the
  failure cause) — [NIST AU-8](https://csrc.nist.gov/pubs/sp/800/53/r5/upd1/final)/[AU-10](https://csrc.nist.gov/pubs/sp/800/53/r5/upd1/final).

### Admin Signature

The `admin_signature` field in `data/reliability_score.json` is an
**Ed25519 signature made with a pinned key** — a fixed verification key
established outside the downgrade path (not chosen, rotated, or supplied per
attempt by the requester). A downgrade approval is only valid when the
signature verifies against that pinned key over the following payload:

```
{tree_hash}|{old_baseline}|{new_baseline}|{reason}|{expires_at}|{jti}
```

| Field | Binding enforced |
|---|---|
| `tree_hash` | Git tree hash of `data/reliability_score.json`'s containing tree at the approved commit — the approval applies to **this** repository state (target binding; the same MUST-subject-digest principle as [SLSA attestations](https://slsa.dev/spec/v1.0/attestation-model#attestation-format), where a subject digest binds the attestation to exactly one artifact) |
| `old_baseline` | The exact floor being lowered; a signature made for one floor cannot be replayed against another |
| `new_baseline` | The exact new floor |
| `reason` | The justification string carried into the audit record |
| `expires_at` | UTC ISO 8601 instant after which the approval is void (signature expiry; [RFC 7519 §4.1.4 `exp`](https://www.rfc-editor.org/rfc/rfc7519#section-4.1.4)) |
| `jti` | Unique token id; each approval is **single-use** — replay of the same `jti` is rejected ([RFC 7519 §4.1.7](https://www.rfc-editor.org/rfc/rfc7519#section-4.1.7)) |

The pair (`old_baseline`, `new_baseline`) in the signed payload prevents
**retargeting**: a signature approving 15.4→14.2 cannot be reused to reach a
different destination floor, and `expires_at` + `jti` prevent an approval from
outliving its window or being replayed ([RFC 8725 §2.7 "signed then
encrypted" / algorithm-and-key validation principles](https://www.rfc-editor.org/rfc/rfc8725#name-validate-cryptographic-ope);
verification keys are pinned, never taken from the request).

`admin_signature` in the downgrade-history entry records **who authorized
the regression** (the pinned key id + signature) — non-repudiation by digital
signature ([NIST SP 800-53 AU-10](https://csrc.nist.gov/pubs/sp/800/53/r5/upd1/final)).

## Cheat Detection

Any modification to `baseline_coverage_pct` in `data/reliability_score.json`
that does **not** have a corresponding entry in `.axiom/bypass_audit.jsonl`
is an **integrity violation**. Detection: the coverage-ratchet gate runner
compares the recorded downgrade history against the current baseline on each
run — for every lowering of `baseline_coverage_pct` there must exist a history
entry whose Ed25519 signature verifies against the pinned key over the payload
above; an unverifiable or missing entry is a ratchet violation. (The former
wording — a `manifest-consistency-gate` that "watches"
`data/reliability_score.json` — described no implemented watcher; the
comparison described here is the runner's own consistency check.)

The `downgrade_history` array in `data/reliability_score.json` is therefore
the reconstructable evidence chain: the full baseline lowering history must be
**reconstructable from the tracked file alone** by verifying each entry's
signature against the pinned key. This makes tampering with the tracked file
itself detectable without access to any untracked local state
(non-repudiation; [NIST SP 800-53 AU-10](https://csrc.nist.gov/pubs/sp/800/53/r5/upd1/final)).

## Exit Codes

| Code | Meaning |
|---|---|
| `0` | PASS (coverage meets or exceeds baseline, or verified + audited downgrade) |
| `1` | FAIL (ratchet violation — no downgrade protocol satisfied, signature invalid/expired/replayed, or audit write failed) |

## Stage Support

**Retracted (2026-10-08, Orphan Gate Authority Closure).** An earlier version of
this section claimed the gate "runs in the `pre-push` and `ci` stages". That was
a false protection claim: the ci.yml retirement (`fa069d610`, 2026-09-16) removed
the last production `bin/gate_hook ci` caller, and no hook or Makefile path ever
invoked the gate at `pre-push`. The gate is wired to no automated stage.

Actual behavior: the gate executes only as a **manual direct-run contract**
(`bin/coverage_ratchet_gate`, manifest stage `manual` since
`src/gate/manifest.d/coverage-ratchet-gate.json` was re-declared honest). Manual
runs may **auto-bump `data/reliability_score.json`** as a side effect — operators
invoking it by hand must expect that write. Re-declaring `pre-push`/`ci` requires
a real dispatch lane first; manifest-consistency-gate Check 10 mechanically
rejects stage claims without call-site evidence. (An even earlier version of
this document claimed `pre-commit` support; the manifest has never registered
the gate for that stage.)
