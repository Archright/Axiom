# UAP Logic Specification

## Purpose
- Defines state space reasoning, counterexample promotion, invariant refinement, automatic repair, and regressionfixation rules for the Universal Acceptance Pipeline (UAP).

## Pipeline Contract
- `axiom universal-acceptance-pipeline` must output AST→IL/SMT2 mapping, vulnerability counterexample search, automatic repair loop, proof artifacts, and BDD generation results as a single JSON contract.
- Legacy verification paths should not be maintained as distributed scripts but converge into a single execution path based on `src/verification/universal_pipeline.nim`.
- UAP results must not bepromoted to safe based solely on SMT's lack of counterexamples, but must be cross-verified with Lean replay and soundness note.

## Counterexample Promotion and Tracking
- Z3 `get-model` results must be promoted as structured JSON bindings and stored consistently in `UniversalPipelineResult.initialScan/finalScan[*].counterExampleInput`.
- SAT counterexamples should not only include model bindings but also summarize key branching points and write paths as structured traces to serve as grounds for invariant reinforcement.
- UAP should not simply patch counterexamples but must generate `refinedInvariant`, `evolutionReasoning`, and `pocSnippet` to be promoted as reusable formal artifacts for subsequent executions.
- `counterexample not found` is not equivalent to `safe`; engine-limited or unverifiable verdicts must be explicitly stated in `soundnessNote` and `verificationVerdictReport`.

## Invariant Refinement Operators
- Refinement must only be performed through `RefinementOperator` dispatcher (`selectOperator` → `applyOperator`), not hardcoded if-else logic.
- All invariants and implications must be encoded as named assertions, and invariants not included in UNSAT core should have their priority lowered or be demoted to inactive candidates.
- Conditional invariants should be promoted as `ImplicationRule` sequences, not boolean flags.
- Operator selection must be performed using fixed seed-based ε-greedy bandit, accumulating success/failure/action rewards to update subsequent priorities.
- Pointer and index family counterexamples must be able to synthesize subject-to-subject relational expressions like `size > index`.
- When identical reward/unsat-core patterns repeat, exploration rate should be incrementally increased to escape stagnation intervals.

## State Space and Semantics Modeling
- `UniversalTranslation` must explicitly extract `stateSpace` and `transitionRelation`.
- Refined invariants must be able to include transition invariants like `next.balance <= state.balance` in addition to state properties.
- The goal of Lean specifications generated by UAP is `Implementation ⊑ Model`, separating implementation into `nextState` and abstract rules into `inductive Step`.
- Lean artifacts must generate `theorem implementation_refines_step` to prove that `nextState` results fall within the allowed range of `Step`.
- `invariant := True` or `stepSpec := True` fallbacks are prohibited; if reasoning results are empty, `strict_spec_warning` must be left and proven promotion must be prohibited.
- Environmental inputs must be modeled as nondeterministic values of `EnvInput`, and `environment_closure` theorems must be maintained for network, file, standard input, and external calls.
- Memory verification must notend with weak constraints like `0 <= idx` but reflect `base + offset ∈ [base, base + length)` range invariants simultaneously in state/transition/SMT constraints.

## Invariant Lifecycle and Proof Vault
- When invariant vulnerabilities are discovered, automatically propose stronger mathematical propositions instead of bypassing with k-increase, and accumulate them in Proof Vault.
- The latest promoted `refinedInvariant` must be automatically re-injected as `activeInvariant` input rule in subsequent UAP executions for the same `modulePath/functionName`.
- The currentSSOT of promoted invariants is the `proof_vault/*_uap_promoted_invariant.json` snapshot.
- Invariants must carry dependency tags, `Suspicious` status, and TTL=`3`, and only directly dependent items undergo deferred re-verification.

## Automatic Repair and Regression Fixation
- Automatic repair snippets must distinguish between Nim and C/C++ `if`/`return` syntax differences and correctly patch them per language.
- `dynamic-proof-search --apply-refinement` on failure must automatically reflect proposed constraints as Nim function signatures or top-of-body `assert` and immediately re-explore.
- Generated PoCs must be automatically placed in `tests/reproduction/` and used as basic regression assets for past violation patterns.
- When vulnerabilities are discovered, `.feature` files that fix counterexamples must be automatically generated under `tests/features/`.
- CI UAP checks must be executed through a single `axiom uap` command, not individual scripts.
