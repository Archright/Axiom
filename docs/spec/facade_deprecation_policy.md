# Facade Deprecation Ratchet Policy

**Created**: 2026-06-13  
**Authority**: AGENTS.md §1.3b (Forwarding Stub 설계 원칙)  
**Enforcement**: `nimtry` architecture gate (`facade-ratchet` query)

## Purpose

The facade deprecation ratchet ensures that forwarding stubs in `src/core/` are monotonically decreasing over time. New forwarding stubs are forbidden; existing stubs must be progressively inlined into their consumers.

## Definitions

### Pure Forwarding Stub

A **pure forwarding stub** is a Nim module that contains ONLY:
- `import` and `export` statements
- Pragmas (`{.push.}`, `{.deprecated.}`, `{.pop.}`)
- Comments and blank lines
- **NO** `func`/`proc`/`type`/`const`/`let`/`var` definitions

Detection is AST-based via `ModuleFacts`:
- `imports.len > 0` (not an empty file)
- `functions.len == 0` (no func/proc)
- `typeDefs.len == 0` (no type definitions)
- `assignments.len == 0` (no const/let/var)

### Hub Module vs Stub

**Hub modules** (e.g., `domain_types.nim`) are forwarding stubs that serve as import encapsulation points per AGENTS.md §1.3a. They are counted in the ratchet but are architecturally justified.

**Deprecated stubs** (18 files) are auto-generated by `tools/generate_forwarding_stubs.nim` with `{.deprecated.}` pragmas. These are the primary targets for inlining.

## Ratchet Mechanism

### Lock File Configuration

```toml
[facade_ratchet]
max_allowed_facades = 4
ratchet_direction = "decrease_only"
count_target = "pure_forwarding_stubs"
```

### Enforcement

1. **Pre-push gate**: `nimtry --query facade-ratchet` runs during pre-push
2. **Baseline**: 6 stubs (as of 2026-06-24; 26→18→8→6 progressive reduction)
3. **Direction**: `decrease_only` — count must never increase
4. **Auto-ratchet**: When a stub is inlined, update `max_allowed_facades` to the new count

### Inlining Procedure

To inline a forwarding stub:

1. Identify all consumers: `grep -r "import core/<stub_name>" src/`
2. Update consumer imports: `import core/<stub_name>` → `import core/<subdir>/<actual_module>`
3. Delete the forwarding stub file
4. Verify: `nim check` passes
5. Update lock file: decrement `max_allowed_facades`

Automated tool: `tools/inline_facade.nim` (single module) or `tools/batch_inline_facades.nim` (batch).

## Hub Stub Justification Audit

**Audited**: 2026-06-24
**Auditor**: Orchestrator agent
**Scope**: All 6 manual hub stubs — WHY each must remain as a facade

### Audit Methodology

For each hub stub, the audit measures:
1. **Direct consumer count**: files that `import` the stub directly
2. **Transitive consumer count**: files reachable through the import chain
3. **Re-export depth**: number of sub-modules or definitions aggregated
4. **Layer spread**: distinct architectural layers touched
5. **Removal cost**: estimated files requiring modification if removed

### Hub Stub: `domain_types`

- **Files**: `src/core/domain_types.nim` (10 lines, pure forwarding) + `src/core/types/domain_types.nim` (32 lines, aggregation)
- **Stub type**: Pure forwarding stub (outer) + aggregation stub (inner)
- **Re-exports from**: 11 sub-modules — `error_types`, `certificate_types`, `solver_types`, `smt_types`, `gate_types`, `verification_types`, `vault_types`, `lean_types`, `refinement_types`, `translation_types`, `symbolic_types_expr`
- **Total definitions aggregated**: 62 (types, funcs, consts across all 11 modules)
- **Direct consumer count**: 36 files
- **Layer spread**: 3 layers (verification: 31, gate: 4, cli: 1)
- **Transitive consumer count**: 36 (terminal — consumers use the types directly)
- **Removal cost**: 36+ files would each need 5–11 individual type imports replaced

**Justification**: Aggregates domain types used across 3 layers and 36 files. Without this hub, every consumer would need to import 5–11 individual type modules (e.g., `import core/types/error_types` + `import core/types/certificate_types` + ...). The outer forwarding stub (`core/domain_types.nim`) enforces AGENTS.md §1 import encapsulation — external layers never reach into `core/types/` internals.

**Recommendation**: **KEEP** — architectural boundary. The aggregation of 11 modules into a single import point for 36 consumers across 3 layers provides critical import encapsulation.

### Hub Stub: `bmc_artifacts`

- **File**: `src/core/bmc/bmc_artifacts.nim` (45 lines)
- **Stub type**: Composition stub — imports 3 BMC sub-modules and composes them into a single artifact
- **Imports**: `bmc_generic`, `bmc_types`, `bmc_variable_map`
- **Defines**: `BmcAnalysisArtifact` (ref object, {.acyclic.}); `initBmcAnalysisArtifact`, `isEmpty` funcs
- **Direct consumer count**: 1 file (`core/orchestration/pipeline_types.nim`)
- **BmcAnalysisArtifact usage**: 6 locations (definition + constructor + isEmpty + pipeline_types field)
- **Transitive consumer count**: pipeline_types feeds into the entire orchestration layer
- **Layer spread**: 2 layers (bmc, orchestration)
- **Removal cost**: 1 direct consumer would need 3 separate BMC imports + inline the composition type

**Justification**: Composes 3 separate BMC type modules (`BmcConfig`, `BmcTransition`, `VariableMapTable`, `ScopeContextStack`) into a single immutable artifact for zero-copy pipeline transport via `{.cursor.}` binding. Without this hub, `pipeline_types.nim` would need to import 3 separate modules and define its own composition type. The artifact is the transport contract between BMC analysis and pipeline orchestration — the `{.acyclic.}` pragma ensures safe ARC lifecycle for heap-allocated pipeline data.

**Recommendation**: **KEEP** — composition artifact. The 3→1 aggregation eliminates import proliferation in the orchestration layer and defines the canonical transport contract for BMC analysis results.

### Key Finding

All 6 manual hub stubs were architecturally justified at review time. 1
(`export_injector`) has since been **removed** (2026-07 dead module cleanup; the
macro library was a zero-import canonical reference). Only 1 of the remaining 5
(`domain_types`) is a pure forwarding stub; the other 4 are active modules with
types, functions, and/or macros that serve as aggregation points or canonical
implementations. The ratchet count of 26 should NOT include these 6 in
deprecation targeting — they are permanent architectural fixtures, not
transitional stubs.
