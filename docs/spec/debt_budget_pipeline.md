# Debt Budget Reconciliation Pipeline Contract

> **Status**: Contract (pending implementation)  
> **Version**: v1.0.0  
> **SSOT**: `data/debt_budgets.json` — metric-definition / budget policy authority  
> **Effective**: This document defines the BUDGET reconciliation pipeline contract. The `--sync-budget` command is not yet implemented in `tools/debt_engine.nim`; all commands below are specified for future implementation.

---

## 1. Data Authority 3-Way Separation

The pipeline operates on three distinct data files, each with a single, non-overlapping authority role. Confusing these roles is a structural violation of the pipeline contract.

### 1.1 Authority Table

| File | Authority Role | Description |
|------|---------------|-------------|
| `data/debt_budgets.json` | **Metric-definition / budget policy authority** | Defines the metric enum, aggregation source, filter predicate, and target for each budget category. This is the *what to measure* and *what the target is* authority. |
| `data/debt_registry.json` | **Observed-state source** | The live, authoritative record of debt entries with their current `status` (open/closed). The pipeline re-derives open/closed counts from this file using the `isOpen()` predicate (see `tools/debt_engine.nim:68-73`). This is the *what is the current state* authority. |
| `data/debt_ledger.json` | **Derived canonical snapshot** | The BUDGET records output of the pipeline. Each record carries `current`, `status`, `resolution`, and `lastVerifiedAt` fields derived from the other two authorities. This is the *what has been computed* authority. |

### 1.2 Terminology Convention

The `debt_registry.json` is **not** referred to as the SSOT in this pipeline. The term "SSOT" is reserved exclusively for `data/debt_budgets.json` (metric definition) and `data/debt_ledger.json` (derived snapshot). The registry is an *observed-state source* — it provides raw observations that the pipeline evaluates, but it does not define policy.

### 1.3 Authority Boundary Rules

1. `debt_budgets.json` defines `metric`, `aggregation source`, `filter predicate`, and `target`. It does **not** contain `current` values computed from the registry.
2. `debt_registry.json` provides the raw observed state. It does **not** contain budget targets or derived BUDGET records.
3. `debt_ledger.json` contains only derived BUDGET records. It must never be manually edited — it is always regenerated by the pipeline.
4. Cross-authority drift (e.g., registry says 42 open entries but ledger BUDGET#005 says `current=0`) is detected by `--validate` and reported as drift.

## 3. Generation Rules Contract

### 3.1 Evaluator-Based Derivation

Each BUDGET record is derived by evaluating the metric definition against the observed state. The evaluator performs the following steps for each metric in `debt_budgets.json`:

1. **Resolve aggregation source**: The `description` field in `debt_budgets.json` specifies the aggregation source (e.g., "open entries in data/debt_registry.json").
2. **Apply filter predicate**: The metric's filter is derived from the `description` semantics (e.g., `isOpen(status)` for `debt_registry_open`).
3. **Compute `current`**: The evaluator counts matching entries from `debt_registry.json`.
4. **Derive `status`**: If `current` meets the `target`, status is `closed`; otherwise `open`.
5. **Resolve `resolution`**: For closed records, resolution is `FIXED` if `current == target`; otherwise `WONT_FIX`.

**BUDGET#005 / BUDGET#006 special cases**: These two records (debt_registry_open and debt_registry_closed) are derived from the registry's live open/closed counts using `isOpen()`. They are **not** hardcoded — they are the evaluator's output for the `debt_registry_open` and `debt_registry_closed` metrics. Any future metric added to `debt_budgets.json` follows the same evaluator path; no special-case branching is permitted.

### 3.2 Deterministic Serialization

- Records are sorted by `id` in ascending order (`BUDGET#001` < `BUDGET#002` < ...).
- JSON keys within each record are in a fixed, documented order (see §5 output schema).
- The generator produces canonical JSON with no trailing whitespace and Unix line endings (`\n`).

### 3.3 Idempotency

Running the generator twice on the same inputs must produce a zero-diff output:

```bash
# Idempotency verification
cp data/debt_ledger.json /tmp/ledger_first.json
./tools/debt_engine --sync-budget
cp data/debt_ledger.json /tmp/ledger_second.json
diff /tmp/ledger_first.json /tmp/ledger_second.json
# Expected: no output (0 bytes diff)
```

### 3.4 Atomic Write

The generator must use atomic write semantics to prevent partial writes:

1. Write to a temporary file (`data/debt_ledger.json.tmp`).
2. `fsync()` the temporary file's file descriptor.
3. `rename()` the temporary file over the target path.

This guarantees that readers never see a partially-written ledger, even if the process is killed mid-write.

### 3.5 Generation Digest

Before writing `debt_ledger.json`, the generator computes a SHA-256 digest of the canonical JSON content (sorted records, fixed key order, no trailing whitespace). The digest is stored in the top-level `generationDigest` field of the ledger. This digest is used by `--validate` to detect unauthorized modifications.

## 4. Command Usage and Output Schema

### 4.1 `--sync-budget`

**Usage**:

```bash
./tools/debt_engine --sync-budget
```

**Behavior**: Evaluates all metrics from `debt_budgets.json` against the current state of `debt_registry.json`, derives BUDGET records, and writes `debt_ledger.json` atomically.

**Output** (stdout):

```
=== Axiom Budget Sync ===
  [sync] metric=import_lint_violations  baseline=36 target=0 current=21  → open
  [sync] metric=layer_violations        baseline=8  target=0 current=2   → open
  [sync] metric=effect_violations       baseline=80 target=0 current=2090 → open
  [sync] metric=nimtry_violations       baseline=704 target=0 current=0  → closed
  [sync] metric=debt_registry_open      baseline=107 target=0 current=0  → closed
  [sync] metric=debt_registry_closed    baseline=0  target=92 current=107 → closed
  [sync] wrote 6 records to data/debt_ledger.json
  [sync] generation digest: sha256:abc123...
```

**Exit code**: `0` on success, `1` on error (missing source files, parse failure).

### 4.2 `--validate`

**Usage**:

```bash
./tools/debt_engine --validate
```

**Behavior**: Validates `debt_ledger.json` against the current state of `debt_budgets.json` and `debt_registry.json`. Checks: schema version, record count, ID format, metric-to-budgetCategory mapping, `current` values match registry-derived counts, generation digest integrity, and idempotency.

**Output schema** (structured JSON on stdout, human-readable summary on stderr):

```json
{
  "validation": {
    "ledgerPath": "data/debt_ledger.json",
    "budgetsPath": "data/debt_budgets.json",
    "registryPath": "data/debt_registry.json",
    "ledgerVersion": "1.1.0",
    "recordCount": 6,
    "generationDigest": "sha256:abc123...",
    "digestMatch": true,
    "idempotent": true
  },
  "records": [
    {
      "id": "BUDGET#001",
      "metric": "import_lint_violations",
      "expected": { "baseline": 36, "target": 0, "current": 21 },
      "committed": { "baseline": 36, "target": 0, "current": 21 },
      "delta": { "baseline": 0, "target": 0, "current": 0 },
      "status": "open",
      "source": "debt_budgets.json",
      "digest": "sha256:def456..."
    }
  ],
  "drift": {
    "hasDrift": false,
    "driftedRecords": [],
    "registryDerived": {
      "debt_registry_open": 0,
      "debt_registry_closed": 107
    }
  },
  "summary": {
    "totalChecks": 12,
    "passed": 12,
    "failed": 0,
    "driftCount": 0
  }
}
```

**Field descriptions**:

| Field | Type | Description |
|-------|------|-------------|
| `validation.ledgerVersion` | string | Expected `"1.1.0"`; fail-closed on mismatch |
| `validation.generationDigest` | string | SHA-256 digest of the ledger content |
| `validation.digestMatch` | boolean | `true` if stored digest matches recomputed digest |
| `validation.idempotent` | boolean | `true` if a second sync produces zero diff |
| `records[].expected` | object | Values from `debt_budgets.json` (baseline, target, current from budget definition) |
| `records[].committed` | object | Values currently stored in `debt_ledger.json` |
| `records[].delta` | object | Difference: `committed - expected` per field |
| `records[].digest` | string | Per-record SHA-256 of the canonical record JSON |
| `drift.hasDrift` | boolean | `true` if any record's `current` does not match registry-derived count |
| `drift.driftedRecords` | array | IDs of records with drift |
| `drift.registryDerived` | object | Live counts derived from `debt_registry.json` via `isOpen()` |
| `summary.totalChecks` | integer | Total number of validation checks performed |
| `summary.passed` | integer | Number of checks that passed |
| `summary.failed` | integer | Number of checks that failed |
| `summary.driftCount` | integer | Number of records with drift |

## 5. Enforcement Ratchet Policy

The enforcement strictness increases over time as the pipeline stabilizes. No enforcement level is ever downgraded.

### 5.1 Current Level: INFO

- `--validate` reports drift as informational output.
- Drift is logged but does not cause a non-zero exit code.
- CI does not fail on drift.
- This level applies until the pipeline has been stable for one release cycle with zero drift incidents.

### 5.2 Future Level: WARN (pending pipeline stabilization)

- `--validate` emits a warning for each drifted record.
- Exit code is `0` but warnings are printed to stderr.
- CI does not fail, but warnings are visible in CI logs.
- Triggered when: pipeline has been stable for one release cycle with zero drift incidents.

### 5.3 Future Level: ERROR / CI hard-fail (pending architect approval)

- `--validate` exits with code `1` on any drift or digest mismatch.
- CI pipeline fails if `--validate` returns non-zero.
- Triggered when: pipeline has been stable at WARN level for one release cycle with zero incidents.
- **CI hard-fail requires architect approval** per AGENTS.md §-1 (CI=0 cutover, 2026-09-20로 `.github/workflows/ci.yml`은 §-1 목록에서 제거·삭제됨 — 원 §-1 불변 인용은 당시 기준) and the hermetic gate framework (`docs/spec/hermetic_gate_framework.md`).

### 5.4 Digest-Mismatch Enforcement

A generation digest mismatch (stored digest ≠ recomputed digest) is always treated as a **potential tampering or unauthorized modification** event, regardless of the enforcement level. This triggers:

1. `--validate` prints an error identifying the specific record(s) affected.
2. Exit code is `1` immediately (no ratchet — this is a security property, not a policy threshold).
3. The event is logged to the audit trail.

## 6. Validate Verification Command Examples

### 6.1 Golden Test

Run the validator against the known-good ledger and confirm zero drift:

```bash
# Golden test: validate against the committed ledger
./tools/debt_engine --validate
# Expected exit code: 0
# Expected stderr: "All debt validation checks passed."
echo "Exit code: $?"
# Expected: Exit code: 0
```

### 6.2 Idempotency Test

Run the sync twice and confirm zero diff:

```bash
# Idempotency test
./tools/debt_engine --sync-budget
cp data/debt_ledger.json /tmp/ledger_run1.json
./tools/debt_engine --sync-budget
cp data/debt_ledger.json /tmp/ledger_run2.json
diff /tmp/ledger_run1.json /tmp/ledger_run2.json
# Expected: no output (zero diff)
echo "Diff exit code: $?"
# Expected: Diff exit code: 0
```

### 6.3 Git Diff Exit-Code Check

Confirm the ledger has no uncommitted changes after a sync:

```bash
# After --sync-budget, check for uncommitted ledger changes
./tools/debt_engine --sync-budget
git diff --exit-code data/debt_ledger.json
# Expected exit code: 0 (no diff — ledger matches committed state)
echo "Git diff exit code: $?"
# Expected: Git diff exit code: 0
```

If the diff is non-zero, the generator is not deterministic or the committed ledger is stale.

### 6.4 Drift Detection Test

Modify the registry to have an open entry, then validate that drift is detected:

```bash
# Introduce a synthetic open entry (temporary)
python3 -c "
import json
with open('data/debt_registry.json') as f: data = json.load(f)
data['entries'].append({
    'id': 'DEBT#TEMP-DRIFT',
    'category': 'Test',
    'description': 'temporary drift test entry',
    'files': [],
    'severity': 'low',
    'source': 'test',
    'status': 'open',
    'resolution': ''
})
with open('data/debt_registry.json', 'w') as f: json.dump(data, f, indent=2)
"
# Now validate — drift should be detected for BUDGET#005 (debt_registry_open)
./tools/debt_engine --validate
# Expected: drift.hasDrift == true, drift.driftedRecords contains "BUDGET#005"
# Restore registry
git checkout data/debt_registry.json
```
