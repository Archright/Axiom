2. MALEBOLGIA CONFIGURATION
================================================================================

2.1 ThreadPoolSize
   - malebolgia's createMaster() does NOT accept a ThreadPoolSize parameter.
   - Thread pool is managed by Nim's std/tasks module, which uses
     countProcessors() to determine pool size.
   - On this system (16 CPUs), the pool will have 16 threads.

2.2 AXIOM_JOBS Usage

   gate_hook.nim (lines 274-275):
     let defaultJobs = max(1, countProcessors() - 2)   → 14 on this system
     let maxJobs = getEnv("AXIOM_JOBS", $defaultJobs).parseInt()

   - Used for logging only in malebolgia context; actual thread pool = countProcessors()

   gate_replay.nim:
     Does NOT reference AXIOM_JOBS or countProcessors() at all.
     Uses createMaster() with default pool size (16 threads).

     - Same formula as gate_hook

   scripts/refresh_cli_binaries.nim (lines 147-151):
     let cpuCount = max(1, cpuinfo.countProcessors())  → 16

   heal_scheduler.nim (lines 66-67, 324-325):

   - StringTableRef in spawn: AVOIDED — env vars set in parent thread before spawn ✓

4. WORKTREE EFFICIENCY (gate_replay)
================================================================================

4.1 Current Approach
   - Creates a git worktree in /tmp/gate-replay-{pid}-{hash} per commit (line 107)
   - Pre-cleanup of leftovers before creation (lines 110-111)
   - Post-cleanup after each commit (line 151)
   - Uses git diff --name-only HEAD~1 to find changed .nim files

4.2 Efficiency Assessment
   - git worktree add --force: Fast operation (creates symlink/copy of files)
   - git diff --name-only: Very fast (index comparison)
   - nim check on changed files only: Fast incremental check
   - Worktree is created and removed per commit: Necessary for isolated check
   - Malebolgia runs all commits in parallel: Each gets its own worktree

4.3 Optimization Opportunities
   - For sequential mode (malebolgia fallback), could reuse a single worktree
     by doing git checkout instead of create/remove per commit
   - Alternative: Use git show <commit>:<path> to extract specific files
     without creating a full worktree
   - For massive ranges (100+ commits), /tmp disk space could be a concern
   - Current approach is acceptable for small replay ranges (<50 commits)

4.4 Conclusion: Worktree approach is sound for parallel execution. Pre/post
   cleanup is correct. Alternative approaches (git show) would be more efficient
   but add complexity. No bugs found.
